## 2. Порівняння за критеріями

| Критерій | SPARQL (RDF) | Cypher (LPG, Neo4j) |
|---|---|---|
| Читабельність | трійкові шаблони, потрібні префікси; зв'язок читається як `?x res:installedAt ?p` | ASCII-шаблон `(e)-[:INSTALLED_AT]->(p)` наочно показує напрямок і тип зв'язку |
| Довжина запиту | довша через PREFIX і окремі трійки для кожної властивості | коротша: властивості в шаблоні вузла, без префіксів |
| Шляхи та графові алгоритми | property paths (`res:dependsOn+`) без обмеження глибини та без повернення самого шляху; немає shortestPath | `*1..4`, `shortestPath`, `nodes(path)`, а також GDS (PageRank, Louvain) |
| Семантика та виведення | RDFS/OWL-виведення, словники (FOAF, schema.org), глобальні IRI, федерація | виведення немає; підкласи моделюються кількома мітками, онтологічна сумісність втрачається |
| Властивості зв'язків | потребують реїфікації або RDF-star | природні: `source`, `confidence`, `validFrom` прямо на зв'язку |
| Цілісність | SHACL (зовнішня перевірка) | обмеження унікальності та індекси в самій СУБД; кардинальності в Community Edition немає |
| Швидкодія на нашому обсязі | 38.62, 21.15, 19.76, 16.74, 23.34 мс (RDFLib у пам'яті) | 4.65, 5.7, 5.39, 5.55, 4.28 мс (Neo4j, разом із мережевим викликом) |

Висновок: для навігації графом, аналізу впливу та алгоритмів зручніший Cypher; для обміну знаннями між системами, виведення та стандартних словників — RDF/SPARQL.

## 3. Text-to-Cypher

**Налаштування.** Підказка `prompts/t2c_system_v1.txt` містить повну схему (мітки, типи й напрямки зв'язків, властивості) і правила: лише читання, лише елементи схеми, обов'язковий LIMIT 50, відмова (`// REFUSED`) на запити зміни даних. Модель: Claude Opus 5.5 (claude.ai).

**Захист (read-only).** Кожен згенерований запит проходить чотири рівні: (1) фільтр заборонених ключових слів (CREATE, MERGE, SET, DELETE, DETACH, REMOVE, DROP, FOREACH, LOAD CSV, CALL) — демонстрація: `MATCH (m:Measurement) DETACH DELETE m` → заборонене ключове слово: DETACH; (2) перевірка, що всі мітки, типи зв'язків і властивості є в схемі; (3) примусовий LIMIT 50, якщо його немає; (4) виконання в режимі «окремий користувач з роллю reader». Спроба запису в такій транзакції: відхилена сервером — Neo.ClientError.Statement.AccessMode.

**Метрика.** Коректних запитів: **9 з 12 (75 %)** (результат збігається з еталоном; додаткові стовпці дозволені). Точний збіг стовпців: 7 з 12. Шкідливий запит (видалення даних): відхилено. Середній час виконання згенерованого запиту: 82.4 мс.

### Аналіз помилок (3)

**t04. Хто з працівників компанії «Захід ВДЕ» виконав найбільше робіт з обслуговування?**

```cypher
MATCH (c:Company {name: 'Захід ВДЕ'})<-[:EMPLOYED_BY]-(e:Employee)<-[:PERFORMED_BY]-(w:MaintenanceWork)
RETURN e.name AS employee, count(w) AS works
ORDER BY works DESC
LIMIT 50
```

**Причина: точне порівняння назви.** Модель записала умову `{name: 'Захід ВДЕ'}`, але в базі компанія називається «ТОВ «Захід ВДЕ»». Підказка містила лише назви властивостей, а не приклади значень, тому модель «вгадала» назву з питання. Запит синтаксично правильний і пройшов усі перевірки, але повернув порожній результат — найнебезпечніший тип помилки, бо користувач може вирішити, що робіт не було. **Виправлення:** додати в підказку приклади значень `name` для довідникових вузлів або правило «для пошуку за назвою використовуй CONTAINS».

Еталон:

```cypher
MATCH (w:MaintenanceWork)-[:PERFORMED_BY]->(e:Employee)-[:EMPLOYED_BY]->(c:Company) WHERE c.name CONTAINS 'Захід ВДЕ' RETURN e.name AS employee, count(w) AS works ORDER BY works DESC, employee
```

**t05. Яке найвище значення температури зафіксували датчики температури і на якій турбіні?**

```cypher
MATCH (m:Measurement)-[:MEASURED_BY]->(s:TemperatureSensor)-[:OBSERVES]->(t:WindTurbine)
RETURN t.name AS turbine, max(m.value) AS maxTemperature
ORDER BY maxTemperature DESC
LIMIT 50
```

**Причина: неправильна гранулярність агрегації.** Питання просить одне найвище значення і турбіну, на якій його зафіксовано, а модель згрупувала дані за турбінами (`max(m.value)` для кожної) і повернула 20 рядків. Перше значення в списку правильне (K-02, 88,5 °C), але відповідь як таблиця не збігається з еталоном. Примусовий LIMIT 50 тут не допоміг, бо модель сама поставила LIMIT 50 замість LIMIT 1. **Виправлення:** у підказці розрізняти «найбільше значення» (ORDER BY … LIMIT 1) і «максимум для кожного» (агрегація), додати приклад.

Еталон:

```cypher
MATCH (m:Measurement)-[:MEASURED_BY]->(s:TemperatureSensor)-[:OBSERVES]->(t:WindTurbine) RETURN t.id AS turbine, m.value AS value ORDER BY value DESC LIMIT 1
```

**t11. Яке обладнання прямо чи опосередковано залежить від підстанції «Львів-Західна»?**

```cypher
MATCH (s:Substation {name: 'Львів-Західна'})<-[:DEPENDS_ON*1..5]-(e:Equipment)
RETURN DISTINCT e.name AS equipment, e.kind AS kind
LIMIT 50
```

**Причина: та сама, що в t04, — точне порівняння назви.** Модель використала `{name: 'Львів-Західна'}`, а в базі підстанція називається «ПС «Львів-Західна»». Структура запиту правильна: шлях змінної довжини `DEPENDS_ON*1..5` у правильному напрямку, `DISTINCT`. Але через назву результат порожній. Помилка повторюється, отже вона системна: без прикладів значень модель не знає форматів назв. **Виправлення:** як для t04, а також перевіряти порожній результат і пропонувати користувачу уточнення («об'єкт з такою назвою не знайдено»).

Еталон:

```cypher
MATCH (x:Equipment)-[:DEPENDS_ON*]->(s:Substation) WHERE s.name CONTAINS 'Львів-Західна' RETURN DISTINCT x.id AS equipment ORDER BY equipment
```
